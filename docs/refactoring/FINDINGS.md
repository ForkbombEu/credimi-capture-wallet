| F-06 | Bug (P2), interoperability | ≈ 0.2 % of generated X.509 certificates carry a non-minimally DER-encoded serial number (`00 xx…`, xx < 0x80). Credo's `CredoWalletWebCrypto.generateRandomValues` returns what the KMS shim returns; the shim `randomBytes: ({ length }) => randomBytes(length)` returns a Node `Buffer`, and `@peculiar/x509`'s `generateCertificateSerialNumber` strips leading zeros with `.slice(n).buffer`, which for a `Buffer` view returns the original unstripped `ArrayBuffer`. OpenSSL (`node:crypto` `X509Certificate`) rejects it with `illegal padding`. Effects: ≈ 0.78 % of `init`/`init --force` runs throw in `validateIssuerMaterial` and keep failing (`init` and `serve`) until `init --force`; ≈ 0.2 % of verifier certificates are malformed without detection and are sent to wallets as `x5c` (strict DER parsers may reject); FCAF fixture certificates are affected the same way; intermittent test failures (`asn1 … illegal padding`). Reproduced deterministically (`/tmp/asn1repro/`), 23/3000 init failures measured. Introduced by `e0ef092`, made visible by `80873ae`. | `src/config.ts:932` (shim), `:873-917` (`writeCertificate`), `:546` (OpenSSL parse); `@peculiar/x509` `x509.es.js:2846-2866` | Return a plain `Uint8Array` from the shim (`new Uint8Array(randomBytes(length))`), optionally validate the verifier certificate with `node:crypto` in `init`; report upstream to `@peculiar/x509` and Credo-TS. Not fixed in this refactoring (behaviour change). Until fixed, validation runs that fail with `illegal padding` are re-run and recorded as F-06. | Open — needs approval |
